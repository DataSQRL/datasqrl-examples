## Requirements Summary

This is a **greenfield DataSQRL batch pipeline** (`spending_insights`) that reads the shared `data-catalog`, computes per-customer spending insights over a bounded recent window, writes them to Iceberg, and serves them over a JWT-authenticated GraphQL/REST/MCP API backed by DuckDB + Vert.x.

In concrete DataSQRL terms the pipeline is:

- **Sources** (all from the catalog, imported under the `data_catalog` namespace): `Unified_Transaction`, `Transaction_Reversal`, `Account`, `Account_Holder`, `Transaction_Category`, `Merchant_Enrichment`, `Recurring_Payment`, `Customer` — plus one **project-owned** source `Fx_Daily_Rate` (a daily currency→USD rate table, test = local JSONL, prod = Iceberg loaded by the bank's treasury feed).
- **Run control & incrementality** (`FR-1..FR-6`): the run is parameterized by a `run_date` (prod default `CURRENT_DATE - 1` UTC, operator-overridable). It recomputes a 7-day window ending on `run_date`, scans source transactions bounded at `read_from = (earliest month touched by the window) − 3 months`, rewrites month-grain outputs for the touched months in full, rewrites transaction-grain outputs for window days only, and is fully deterministic (no wall-clock values; ties broken by explicit keys).
- **Classification & currency** (`FR-7..FR-19`): convert amounts to USD via `Fx_Daily_Rate` at the transaction's `posted_date` with carry-forward fallback (USD = 1.0; missing rate → exclude + count); include only `POSTED`/`DEBIT` spending and `POSTED`/`CREDIT` income on `CHECKING`/`SAVINGS` accounts; exclude internal transfers (marked category/type **and** a deterministic same-customer pairing rule); net `PARTIAL`/`CORRECTION` reversals against the original transaction at the original's business date; resolve category to level-1 + level-2 (null → `Uncategorized`) and merchant to enriched name (null → `Unknown merchant`).
- **Insights** (`FR-20..FR-30`): category spending (L1 + L2) with a 3-month normal-spending baseline and a "much more than usual" flag (≥50% and ≥$75), top-5 merchants + per-category merchants, recurring-payment monthly cost (frequency-normalized) + total + a "became more expensive" flag (≥5% and ≥$1), unusually-large purchases (≥3× a 90-day baseline mean and ≥$200), monthly/account/daily cash flow (income, spending, net, savings rate), and a partial-month marker for the month containing `run_date`.
- **Outputs** (14 Iceberg tables, keyed as stated in the request's "Transformations and aggregations" table): `Customer_Month_Category_L1_Spending`, `Customer_Month_Category_L2_Spending`, `Customer_Month_Top_Merchant`, `Customer_Month_Category_Merchant`, `Customer_Recurring_Payment`, `Customer_Recurring_Monthly_Total`, `Customer_Large_Purchase`, `Customer_Month_Cash_Flow`, `Customer_Account_Month_Cash_Flow`, `Customer_Day_Spending`, `Customer_Account_Day_Spending`, `Pipeline_Run_Metric`, `Uncategorized_Spending_Daily`, `Fx_Daily_Rate`.
- **Monitoring** (`FR-31..FR-32`): `Pipeline_Run_Metric` (one row per run) and `Uncategorized_Spending_Daily` (one row per window day).
- **API** (`FR-33`): 13 named query operations (no mutations/subscriptions), `endpoints: OPS_ONLY`, `authKind: ["JWT"]` HS256 (issuer `spending-insights`, audience `spending-console`), any signed-in staff user reads any customer.
- **Engines**: `["flink", "iceberg", "duckdb", "vertx"]` — batch Flink, Iceberg warehouse, DuckDB as the query engine, Vert.x API. No `postgres` (no DB-backed serving tables) and no `kafka` (no subscriptions/mutations).

**UI is required.** The request specifies a five-screen staff web application (customer search, month overview, categories, recurring payments, large purchases) that reads every number from the named API operations and performs no aggregate of its own. The plan includes `/implement-ui` checklist steps.

**Custom UDFs: none required.** Frequency-normalized monthly cost and rounding are expressible with Flink SQL arithmetic + `ROUND`; the internal-transfer pairing and reversal netting are SQL joins/aggregations. See `## Technical Decisions` (D-8).

## Requirements Reference

Every functional requirement (FR), non-functional requirement (NFR) and decision (D) cited in this plan, with its full text. The request's NFRs are unnumbered prose; this plan assigns them stable identifiers (`NFR-1`…`NFR-8`) so they can be cited.

### Functional requirements

- **FR-1** — Accept a run date as configuration. In production it defaults to the last full day in UTC (`CURRENT_DATE - 1`). An operator can set it explicitly to re-run a failed night.
- **FR-2** — Recompute a **7-day window** ending on the run date, inclusive: `window_start = run_date - 6 days`, `window_end = run_date`. See [Why 7 days](#why-the-window-is-7-days).
- **FR-3** — Bound the source scan. Read source transactions only for `posted_date BETWEEN read_from AND run_date`, where `read_from` is the first day of the earliest month touched by the window, minus 3 calendar months. The scan is at most ~4 months of data per run and does not grow as history grows.
- **FR-4** — Rewrite month-grain outputs only for the months the window touches (1 or 2 months), and rewrite those months **in full** from source, not just the window days. Rows for every earlier month stay exactly as the previous run left them.
- **FR-5** — Rewrite transaction-grain outputs only for `posted_date` within the window. Rows outside the window stay as the previous run left them.
- **FR-6** — Produce identical output for identical `run_date` and identical input. No wall-clock value, no `CURRENT_TIMESTAMP`, and no non-deterministic ordering appears in business logic; every date is derived from `run_date`. Ties in any ranking are broken by an explicit deterministic key.

### Currency

- **FR-7** — Maintain a project-owned daily FX rate table `Fx_Daily_Rate`, keyed by `(currency_code, rate_date)`, carrying `usd_per_unit`.
- **FR-8** — Convert every transaction amount to USD at the rate for its **business date** (`posted_date`) in its `currency_code`. `USD` converts at exactly 1.0.
- **FR-9** — When no rate exists for that currency on that date, use the most recent earlier rate for that currency. When no earlier rate exists either, exclude the transaction from every insight and count it in `missing_fx_rate_txn_count` (FR-31).

### What counts

- **FR-10** — Include only transactions on a deposit account whose `account_type` is `CHECKING` or `SAVINGS`. Exclude `MONEY_MARKET`, `CD` and `IRA`.
- **FR-11** — Count **spending** as a transaction that is `POSTED`, `DEBIT`, on an in-scope account, not an internal transfer (FR-14), and not a `REVERSAL` row.
- **FR-12** — Count **income** as a transaction that is `POSTED`, `CREDIT`, on an in-scope account, not an internal transfer (FR-14), and not a `REVERSAL` row.
- **FR-13** — Exclude every transaction whose status is `PENDING`, `REVERSED` or `RETURNED` from all insight aggregates. A `PENDING` transaction enters the insights on a later run once it posts, which the 7-day window guarantees.
- **FR-14** — Treat a transaction as an **internal transfer** when either rule matches, and exclude it from spending, income and cash flow:
  - **(a) marked** — its category resolves to the `Transfers` top-level category, or its `transaction_type` is one of `TRANSFER_IN`, `TRANSFER_OUT`, `INTERNAL_TRANSFER`.
  - **(b) paired** — a `POSTED` `DEBIT` and a `POSTED` `CREDIT` of the same customer, equal USD amount, on two **different** in-scope accounts of that customer, with `posted_date` at most 1 day apart, where neither row matched rule (a). Each debit pairs with at most one credit; when several candidates match, the one with the smallest `transaction_id` wins, so the pairing is deterministic.
- **FR-15** — Net **partial refunds and corrections** against the original transaction. For every row in `Transaction_Reversal` whose `reversal_type` is `PARTIAL` or `CORRECTION` and whose original transaction is still `POSTED`, subtract `reversal_amount_cents` (converted to USD at the **original** transaction's business date) from that original transaction's contribution to every insight. The netted amount floors at zero. The reversing row itself is excluded by FR-11 and FR-12. Apply a reversal only when the reversing transaction's own `posted_date` is on or before `run_date`, so a run never sees a refund that had not happened yet and a re-run of an old date reproduces what that night knew.
- **FR-16** — Attribute a reversal to the **original** transaction's `posted_date`, month, category, merchant and account — never to the reversing row's own date. When that original date falls before `window_start`, count the reversal in `late_transaction_count` (FR-31) rather than silently dropping it.
- **FR-17** — Resolve each transaction's **category** through `Transaction_Category` to both its level-2 category and its level-1 ancestor. A transaction with a null `category_id`, or one that does not resolve, is reported under the synthetic category `Uncategorized` at both levels.
- **FR-18** — Resolve each transaction's **merchant** to `merchant_id` and the cleaned merchant name from `Merchant_Enrichment`, falling back to the transaction's own `merchant_name`. A transaction with no merchant is reported under the synthetic merchant `Unknown merchant`. 45% of debits in the test data carry no merchant, so this bucket is normal, not an error.
- **FR-19** — Assign every transaction to the calendar day and calendar month of its `posted_date` in UTC.

### Insights

- **FR-20** — For each customer, month and **level-1** category, and for each customer, month and **level-2** category, compute spending in USD and a transaction count.
- **FR-21** — For each of those rows, compute **normal spending**: the mean spending of that customer in that category over the **3 complete calendar months** before the month, counting a month with no spending in that category as zero. Normal spending is null unless the customer's earliest in-scope transaction falls on or before the start of that 3-month baseline.
- **FR-22** — Flag **much more than usual** when the month is complete, normal spending is not null, the month's spending is at least **50% above** normal spending, **and** the excess is at least **$75.00**. Report `excess_usd_cents` and `excess_pct` alongside the flag. The flag is computed independently at level 1 and at level 2.
- **FR-23** — For each customer and month, rank merchants by USD spending and keep the **top 5**, breaking ties by merchant name ascending then `merchant_id` ascending. Also compute merchant spending within each level-2 category, for the category drill-down.
- **FR-24** — For each customer, list their recurring payments from `Recurring_Payment` with a **monthly cost** derived from `typical_amount_cents` and `frequency`: `WEEKLY x 52/12`, `BIWEEKLY x 26/12`, `MONTHLY x 1`, `QUARTERLY / 3`, `ANNUAL / 12`, rounded half-up to whole cents.
- **FR-25** — For each customer, compute the **total monthly recurring cost** as the sum of the monthly cost of their `ACTIVE` series only.
- **FR-26** — Flag a recurring payment as **became more expensive** when its latest posted charge is at least **5% above** the previous posted charge on the same series **and** at least **$1.00** above it. Report `previous_charge_usd_cents`, `latest_charge_usd_cents`, `latest_charge_date`, `increase_usd_cents` and `increase_pct` for every series with two or more posted charges, whether or not it is flagged. Also surface `typical_amount_usd_cents` and `amount_variance_usd_cents` from the catalog as context, without using them for the flag.
- **FR-27** — Flag a spending transaction as an **unusually large purchase** when its USD amount is at least **3x** the mean USD amount of that customer's spending transactions in the **90 days before** its `posted_date`, **and** at least **$200.00**. A customer with fewer than **5** such prior transactions has no baseline and no flag. Report the amount, the baseline mean and the ratio.
- **FR-28** — For each customer, account and month, and for each customer and month across all their in-scope accounts, compute **cash flow**: income, spending, net (`income - spending`) and savings rate (`net / income`). The savings rate is null when income is zero. The customer-level savings rate is computed from summed income and summed spending, never as an average of per-account rates.
- **FR-29** — For each customer, account and day, and for each customer and day, compute **daily spending** in USD, for the month-overview chart.
- **FR-30** — Mark the month containing the run date as a **partial month** (`is_partial_month`) covering days 1 through `run_date`. Suppress the normal-spending comparison for a partial month: `normal_spend` and the much-more-than-usual flag are null. Every other month is complete.

### Monitoring

- **FR-31** — Write one `Pipeline_Run_Metric` row per run, keyed by `run_date`, carrying: `run_date`, `window_start`, `window_end`, `recomputed_day_count`, `recomputed_months`, `transaction_count_processed`, `late_transaction_count`, `missing_fx_rate_txn_count`. A transaction is **late** when its enrichment timestamp (`Unified_Transaction.computed_at`) falls on the run date but its `posted_date` is before `window_start` — it arrived or changed after the window had already moved past it. This number is the evidence for whether 7 days is long enough.
- **FR-32** — Write one `Uncategorized_Spending_Daily` row per day in the window, carrying `spend_date`, total spending USD, uncategorized spending USD, the uncategorized **share** of spending, total transaction count and uncategorized transaction count. A break in the upstream categorization shows up here the next morning.

### API and application

- **FR-33** — Expose one named API operation per screen element (listed under [API surface](#api-surface)). Every operation requires a valid JWT. Any signed-in staff user may read any customer, so no operation filters by the caller's identity.
- **FR-34** — Serve a staff web application with the five screens below. Every number it displays comes from an API operation; the application computes no aggregate of its own.

### Non-functional requirements (assigned identifiers)

- **NFR-1 (Freshness)** — results for day D are available by 06:00 UTC on day D+1, measured from the source tables being complete for day D to the API serving the new rows. The job is scheduled at 02:00 UTC.
- **NFR-2 (Run time)** — a nightly run completes within 30 minutes at the assumed production volume.
- **NFR-3 (Read volume)** — bounded at roughly 4 months of transactions per run (FR-3), constant as history grows. This is the measurable form of "must not read the whole history every night".
- **NFR-4 (Throughput)** — batch; there is no per-second rate to sustain. Above the assumed volume the run takes proportionally longer and the 06:00 UTC target is the first thing to break.
- **NFR-5 (Retention)** — insight tables keep 36 months of months. `Pipeline_Run_Metric` and `Uncategorized_Spending_Daily` keep 400 days. Rows past the boundary are deleted by a separate maintenance job, not by this pipeline.
- **NFR-6 (PII & sensitive fields)** — outputs carry `customer_id`, `account_id`, merchant names, category names, dates and USD amounts. No SSN, date of birth, address, contact detail, cleartext account number, running balance, or transaction description reaches any output table or any API response. Customer display name appears only in `CustomerSearch`. Amounts are GLBA NPI, so every operation requires a JWT (FR-33).
- **NFR-7 (Compliance)** — GLBA, GDPR and CCPA apply through the catalog's Restricted classification. Right to erasure is satisfied by deleting a customer's rows from the insight tables; because outputs are keyed on `customer_id`, this is a bounded delete and needs no recompute.
- **NFR-8 (Availability)** — a failed night is recovered by re-running with the same `run_date` (FR-1), which is safe because every write is keyed and idempotent (FR-6). The API keeps serving the previous night's results while a run is in progress; readers never see a partially written month.

### Decisions already fixed by the request

- **D-1 (Window length = 7 days)** — chosen against the catalog's measured lags: reversal lag max 5 days, ACH/wire return lag max 4 days, enrichment lag median 0.12 d (12 rows > 3 d, 2 > 7 d). 7 days covers the reversal max of 5 and return max of 4 with two days of headroom, keeps the scan bounded, and leaves the enrichment tail visible through `late_transaction_count`. If that counter is consistently non-zero in production, the window is the single value to raise.

## API Contract

Protocols `GRAPHQL`, `REST` and `MCP`, `endpoints: OPS_ONLY`, so only the named operations below are reachable. Every operation requires a valid JWT. The contract is realized as an explicit GraphQL schema (`spending_insights-api/schema.v1.graphqls`) plus a named-operations file (`spending_insights-api/operations.v1.graphql`); see `## Implementation Checklist`. Operation names below are the contract — do not rename them.

### Queries

| Operation | Parameters | Returns | Screen |
|---|---|---|---|
| `CustomerSearch` | `customerId` | customer id, display name, status, count of in-scope accounts | 1 |
| `CustomerAccounts` | `customerId` | the in-scope accounts of that customer only: `accountId`, masked account number, type, status | 2 |
| `MonthOverview` | `customerId`, `month`, `accountId` (optional) | income, spending, net, savings rate, `isPartialMonth` | 2 |
| `DailySpending` | `customerId`, `month`, `accountId` (optional) | one row per day: date, spending USD | 2 |
| `CategorySpending` | `customerId`, `month` | per level-1 category: name, spending, normal spending, `isMuchMoreThanUsual`, excess amount, excess pct, with level-2 children nested | 3 |
| `CategoryMerchants` | `customerId`, `month`, `categoryId` | merchants under that category: name, spending, transaction count | 3 |
| `TopMerchants` | `customerId`, `month` | the top 5 merchants of the month with spending and count | 3 |
| `RecurringPayments` | `customerId` | per series: merchant, type, frequency, monthly cost, latest and previous charge, `becameMoreExpensive`, increase amount and pct, status | 4 |
| `RecurringTotal` | `customerId` | total monthly recurring cost across ACTIVE series | 4 |
| `LargePurchases` | `customerId`, `fromDate` (optional), `toDate` (optional) | date, merchant, category, amount, baseline mean, ratio | 5 |
| `RunMetrics` | `limit` (optional) | the most recent run metric rows | ops |
| `UncategorizedShare` | `fromDate`, `toDate` | per day: total spending, uncategorized spending, share | ops |

`month` is accepted as `YYYY-MM`. Omitting `accountId` means all in-scope accounts of the customer.

### Mutations and subscriptions

None. This pipeline is read-only for its consumers.

### Access

- Vert.x `authKind: ["JWT"]`, HS256, secret from `${SPENDING_INSIGHTS_API_JWT_SECRET}`, issuer `spending-insights`, audience `spending-console`.
- Authorization is binary: a valid token grants access to every customer (FR-33). No operation filters on a tenant or a caller claim, because any signed-in staff user may open any customer.
- No operation returns SSN, date of birth, address, account number in the clear, or the running balance.

### Web application

A single-page application served as static files, five screens, signing in with a staff JWT and holding the opened customer in shared state so every screen follows it.

1. **Customer search** — enter a customer id, open that customer. Every other screen follows.
2. **Month overview** — month picker and an optional account picker limited to that customer's in-scope accounts. Shows money in, money out, what is left, and the share of income left, plus a daily spending chart for the chosen month. The current month renders as "month so far" with the comparison hidden.
3. **Categories** — level-1 categories for the chosen month with spending, normal spending and the much-more-than-usual flag; expanding a row shows its level-2 children, and expanding one of those shows the merchants behind it.
4. **Recurring payments** — every series with its monthly cost, the total monthly cost, and a marker on the ones that became more expensive.
5. **Large purchases** — date, merchant and amount for each unusually large purchase.

Every figure on every screen maps to one of the operations above. The application performs no arithmetic across API responses.

## Scenario Analysis

**Axis 1 — Artifact type: `pipeline`.** The request builds a DataSQRL *pipeline*: it ingests from catalog sources, runs non-trivial transformations/aggregations (FX conversion, classification, reversal netting, internal-transfer pairing, five insight families), writes results to Iceberg, and serves a GraphQL/REST/MCP API via DuckDB + Vert.x. Files are `.sqrl` scripts plus `*-package.json`. It is emphatically *not* a catalog: the catalog already exists and is read-only; this project defines no `_schema` catalog tables of its own except the single project-owned source `Fx_Daily_Rate`. This drives the `pipeline` verifiers.

**Axis 2 — Task type: `new-project`.** The project root contains no `.sqrl` or `*-package.json`; this is a build-from-scratch. Although the request fully specifies the architecture (window, tables, keys, API surface, acceptance criteria), the *task* is to stand up a new pipeline: sources are known, processing/aggregations are enumerated (FR-7…FR-32), the API is fixed (13 named operations), engines are determined (`flink`, `iceberg`, `duckdb`, `vertx`), the nearest template is `/opt/sqrl_templates/finance/customer/`, and no custom UDFs are required. `architecture-design` is not selected because the architecture has already been decided in the requirements; `extend-project` and `connector-setup` are inapplicable because there is nothing to extend.

**Engines (minimal set).** `flink` (always, batch `execution.runtime-mode = BATCH`); `iceberg` + `duckdb` (outputs are Iceberg tables; DuckDB is the only full query engine that can serve the API and run tests over them); `vertx` (GraphQL/REST/MCP API). Omitted: `postgres` (no database-backed serving tables — everything is a data-lake read), `kafka` (no `SUBSCRIBE` and no `/*+engine(kafka)*/` mutation table — the pipeline is read-only), and all shallow Iceberg query engines (no external engine requirement).

**Domains.** `finance` (transactions, spending, cash flow, recurring payments, FX) and `analytics` (per-customer KPIs, dashboards, BI).

## Test Data Specification

The catalog's own test data already covers every transaction-level edge case the pipeline must handle; this project **adds only one test-data file**, `testdata/fx_daily_rate.jsonl` (the FX rate table the catalog lacks). Everything else is read from the catalog's `-test` connectors.

### Project-owned test data: `testdata/fx_daily_rate.jsonl`

Purpose: exercise FR-8 (USD = 1.0), FR-9 carry-forward (a missing day falls back to the latest earlier rate) and FR-9 missing-rate (a currency with no rate at all is excluded and counted), directly through the FX-resolution logic — even though every catalog transaction is USD.

Records (JSONL; one per line):

- **FX-USD-1** — `currency_code USD`, `rate_date 2026-08-27`, `usd_per_unit 1.000000`, `rate_source INTERNAL`. Exercises USD = 1.0.
- **FX-USD-2…N** — one `USD` row per window day `2026-08-27`…`2026-09-05`, each `usd_per_unit 1.000000`. Keeps the identity conversion well-defined for the whole window.
- **FX-EUR-1** — `currency_code EUR`, `rate_date 2026-08-30`, `usd_per_unit 1.085000`. Earliest EUR rate.
- **FX-EUR-2** — `currency_code EUR`, `rate_date 2026-08-31`, `usd_per_unit 1.087400`. The rate a EUR transaction on the missing day must carry forward to.
- *(deliberate gap)* — no EUR row for `2026-09-01`. The carry-forward target.
- **FX-EUR-3** — `currency_code EUR`, `rate_date 2026-09-02`, `usd_per_unit 1.089000`. Proves carry-forward stops at the *most recent earlier* rate, not any later one.
- **FX-GBP-1** — `currency_code GBP`, `rate_date 2026-09-02`, `usd_per_unit 1.250000`. A normal non-USD currency with a present rate.
- *(JPY)* — **no rows at all** for `currency_code JPY`. A currency with no rate and no earlier rate → missing-rate path.

Expected resolution outcomes (asserted by a `/*+test */` snapshot on the FX-resolution intermediate, since no catalog transaction is non-USD):

- `(USD, any date)` → `usd_per_unit 1.000000`.
- `(EUR, 2026-09-01)` → `usd_per_unit 1.087400` (carry-forward from `2026-08-31`).
- `(EUR, 2026-09-02)` → `usd_per_unit 1.089000` (exact match, no fallback).
- `(GBP, 2026-09-02)` → `usd_per_unit 1.250000`.
- `(JPY, any date)` → no rate → transaction excluded from every insight and counted in `missing_fx_rate_txn_count`.

## Technical Decisions

- **D-2 — Batch execution and bounded catalog reads.** Flink runs `execution.runtime-mode = BATCH`, and the catalog is included with `is_batch: true` so its Kafka CDC sources switch to `scan.bounded.mode = latest-offset` and its filesystem sources drop `source.monitor-interval`. Constraint: nightly cadence, no sub-daily freshness (NFR-1/NFR-4), bounded sources.

- **D-3 — Dedup the Kafka-CDC catalog sources; trust the Iceberg sources.** `Customer`, `Account`, `Account_Holder` and `Transaction_Reversal` are Kafka change streams in prod, so a bounded batch read sees every historical version. Each is collapsed to its latest snapshot with `DISTINCT` ordered by `source_updated_at DESC` (Customer on `customer_id`, Account on `account_id`, Account_Holder on `(account_id, customer_id)`, Transaction_Reversal on `reversal_id`). The four enriched sources are Iceberg upsert tables (one row per key) and are read as-is. Constraint: the catalog's prod connectors (`core_transactions-prod.sqrl`, `deposit_accounts-prod.sqrl`, `customer_master-prod.sqrl`) are Kafka CDC, while `enriched_transactions-prod.sqrl` is Iceberg upsert.

- **D-4 — Run date is mustache-templated configuration, not wall-clock.** `run_date` is supplied through `script.config.run_date` when set; when absent (prod) it falls back to `CURRENT_DATE - 1` day. Every other date (window, `read_from`, month, baselines) derives from `run_date`. Constraint: FR-1 (operator override to re-run a failed night) and FR-6 (determinism; `CURRENT_TIMESTAMP` never appears in business logic).

- **D-5 — `month` is a `DATE` set to the first day of the month.** It sorts and joins cleanly; the API accepts `YYYY-MM` and each operation parses it to a first-of-month `DATE`. Constraint: the request's "month is a DATE set to the first day of the month".

- **D-6 — Incrementality via keyed Iceberg upsert, not full-table rewrite.** Every output table is an Iceberg sink with `PRIMARY KEY NOT ENFORCED` and `write.upsert.enabled = true`. Month-grain queries emit only the affected months (in full); transaction-grain queries emit only window days. Upsert overwrites same-key rows and leaves every other key byte-identical (FR-4/FR-5). Constraint: FR-3..FR-6 — the scan must not grow with history and older rows must stay as the previous run left them.

- **D-7 — Two test sub-projects prove incrementality and the as-of-run-date rule.** `spending_insights` (`run_date = 2026-09-02`, snapshots under `snapshots/spending_insights/`) and `spending_insights_replay` (`run_date = 2026-09-05`, snapshots under `snapshots/spending_insights_replay/`), each with its own `-b` build dir. The replay's snapshot is the only evidence that the `2026-09-04` refund demotes the `2026-09-02` large-purchase row (FR-5/FR-15/FR-27). Constraint: the acceptance criteria require comparing two different run dates over the same input.

- **D-8 — No custom UDFs.** Frequency-normalized monthly cost (WEEKLY × 52/12, BIWEEKLY × 26/12, MONTHLY × 1, QUARTERLY ÷ 3, ANNUAL ÷ 12) and half-up rounding to whole cents are expressible with Flink SQL arithmetic and `ROUND`; the internal-transfer pairing and reversal netting are joins/aggregations with deterministic tie-breaks. Constraint: the request enumerates no logic that Flink SQL cannot express.

- **D-9 — FX resolution is a testable intermediate.** Because every catalog transaction is `USD`, the carry-forward and missing-rate paths cannot be exercised end-to-end by a real transaction. The resolution (a mapping from `(currency_code, posted_date)` to `usd_per_unit`) is therefore built as a named intermediate and proven by a `/*+test */` snapshot against the FX test data (`USD`→1.0, `EUR` on a missing day → earlier rate, `JPY`→no rate), while the full-pipeline `missing_fx_rate_txn_count` is expected to be 0. Constraint: the request's Fx test-coverage note ("no catalog transaction is non-USD").

- **D-10 — JWT HS256 with `endpoints: OPS_ONLY`.** Vert.x `authKind: ["JWT"]`; HS256 secret from `${SPENDING_INSIGHTS_API_JWT_SECRET}` (base64-encoded into `buffer`), issuer `spending-insights`, audience `spending-console`. Only the 13 named operations are reachable; no mutations/subscriptions. Constraint: FR-33 and the request's Access section.

- **D-11 — No-positive-test rules are implemented and snapshotted, not skipped.** The paired-transfer intermediate (FR-14b) snapshots empty; every 2+-charge recurring series snapshots with `increase_usd_cents = 0` / `increase_pct = 0.00` / `becameMoreExpensive = false` (FR-26); the full-pipeline missing-rate counter is 0 (FR-9). The snapshots are the regression evidence that each rule is computed. Constraint: the request's open questions (no positive test for paired transfers, price increases, or missing FX).

## Assumptions

- **Production transaction volume and customer count**: Assumed 5 million transactions per night across 2 million customers, and the 30-minute target (NFR-2) is sized against that. Rationale: the request's recommended default; the test data (8,688 rows / 492 customers) gives no signal on production scale. [impact: high]

- **Iceberg warehouse and catalog for this project's outputs**: Assumed a separate `spending_insights` warehouse under `${SPENDING_INSIGHTS_ICEBERG_WAREHOUSE}`, Hadoop catalog, database `insights`, matching the catalog's conventions. Rationale: the request's recommended default; isolates this project's tables from the catalog's `${DEPOSITS_PAYMENTS_ICEBERG_WAREHOUSE}`. [impact: low]

- **Who loads `Fx_Daily_Rate` in production**: Assumed the bank's existing treasury rate feed writes the Iceberg table before 01:00 UTC, and this project only reads it; a missing day is handled by the FR-9 carry-forward rule. Rationale: the request defines and reads the table but does not name the loader. [impact: medium]

- **Paired-transfer rule has no positive test**: Assumed implement FR-14(b), snapshot its intermediate as empty, and revisit if production shows unmarked transfers. Rationale: `counterparty_account_id` is null on all core transactions, so the stronger same-owner check is unavailable. [impact: medium]

- **Recurring price increase has no positive test**: Assumed implement FR-26, snapshot the per-series comparison, and accept zero flags in test; raise the missing test data with the transactions team. Rationale: the catalog bills an identical amount every time (max/min ratio 1.000). [impact: medium]

- **Joint accounts are counted in full for every holder**: Assumed a joint account's spending appears in full under each active holder rather than split by `ownership_percentage`. Rationale: a service agent answering a call about a shared account wants the account's real total; 215 joint holdings are affected. [impact: medium]

- **Closed, dormant and frozen accounts**: Assumed include transactions from accounts in any status (a closed account's history is still part of how the customer spent); only `CustomerAccounts` filters to `OPEN` for the account picker. Rationale: the request's recommended default. [impact: low]

- **Cash withdrawals count as spending**: Assumed the 577 `WITHDRAWAL` transactions (category `Cash Withdrawal` under `Financial`) count as spending. Rationale: the money left the deposit account; the category makes them identifiable. [impact: low]

- **Bank fees and interest**: Assumed `FEE`/`OVERDRAFT_FEE` (223 rows) count as spending under `Financial`, and `INTEREST` credits (316 rows) count as income. Rationale: both change what is left at the end of the month. [impact: low]

- **JWT issuance**: Assumed validate HS256 tokens from an existing internal identity provider using a shared secret, and issue no tokens from this project. Rationale: the request specifies JWT but not the issuer; a different algorithm or a JWKS endpoint would change the Vert.x config. [impact: medium]

- **The missing-FX and carry-forward paths are proven at the FX-resolution unit level, not end-to-end**: Assumed the full-pipeline `missing_fx_rate_txn_count` is 0 on catalog data (all USD) and the detection paths are proven by a `/*+test */` snapshot over the FX-resolution intermediate. Rationale: no catalog transaction is non-USD, so an end-to-end non-USD path cannot be constructed without inventing source data. [impact: low]

- **Test replay is a second sub-project, not a second environment**: Assumed `spending_insights_replay` differs from `spending_insights` only by `run_date` (and `snapshot-folder`), sharing the base and the `test` environment for catalog reads. Rationale: `run_date` is baked at compile time, so a different value needs its own compile/build dir. [impact: low]
