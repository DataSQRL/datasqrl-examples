# Requirements: Spending Insights

Source request: [`adr/my_request.md`](my_request.md). This document is self-contained; the planner
reads this file only.

Project name: `spending_insights`. Repository root is the project root (the git prefix is empty),
so the main script is `spending_insights.sqrl` beside `spending_insights-shared-package.json`.

---

## Goal

Give bank staff one agreed set of spending numbers per customer, so a service agent on a call and a
product analyst in a meeting quote the same figure. A nightly Flink batch job reads the shared data
catalog, computes per-customer spending insights over a short recent window, and writes them to
Iceberg. DuckDB queries those tables and Vert.x serves them to an internal staff web application
over an authenticated API.

## Scope

**In scope**

- One DataSQRL project, `spending_insights`, with a single nightly batch deployment.
- Five insight families: category spending with a normal-spending comparison, top merchants,
  recurring payments with monthly cost and price increases, unusually large purchases, and monthly
  cash flow.
- A currency conversion table that this project owns and this project builds.
- Incremental recomputation over a bounded window, driven by an explicit run date.
- Two monitoring outputs: per-run counters and a daily uncategorized-spending share.
- A GraphQL/REST API with one named operation per screen element, authenticated with JWT.
- A staff web application with five screens, reading every number from that API.

**Out of scope**

- Changing the `data-catalog` submodule. It is mounted read-only and this project builds on it.
- Credit card spending. Credit cards live in the Lending line of business and are excluded by the
  request; only deposit accounts of type `CHECKING` and `SAVINGS` count.
- Streaming or sub-daily freshness. Nightly is the agreed cadence and the reason the cost is low.
- Customer-facing surfaces. Every consumer is internal staff.
- Detecting recurring payments. The catalog's `Recurring_Payment` table already does that; this
  project turns it into a monthly cost and a price-increase signal.
- Categorizing transactions. Categories come from the transactions team; this project reports the
  share that is missing rather than filling it in.
- Writing back to any catalog table.

## Functional requirements

### Run control and incrementality

- **FR-1**: Accept a run date as configuration. In production it defaults to the last full day in
  UTC (`CURRENT_DATE - 1`). An operator can set it explicitly to re-run a failed night.
- **FR-2**: Recompute a **7-day window** ending on the run date, inclusive:
  `window_start = run_date - 6 days`, `window_end = run_date`. See
  [Why 7 days](#why-the-window-is-7-days).
- **FR-3**: Bound the source scan. Read source transactions only for
  `posted_date BETWEEN read_from AND run_date`, where `read_from` is the first day of the earliest
  month touched by the window, minus 3 calendar months. The scan is at most ~4 months of data per
  run and does not grow as history grows.
- **FR-4**: Rewrite month-grain outputs only for the months the window touches (1 or 2 months), and
  rewrite those months **in full** from source, not just the window days. Rows for every earlier
  month stay exactly as the previous run left them.
- **FR-5**: Rewrite transaction-grain outputs only for `posted_date` within the window. Rows outside
  the window stay as the previous run left them.
- **FR-6**: Produce identical output for identical `run_date` and identical input. No wall-clock
  value, no `CURRENT_TIMESTAMP`, and no non-deterministic ordering appears in business logic; every
  date is derived from `run_date`. Ties in any ranking are broken by an explicit deterministic key.

### Currency

- **FR-7**: Maintain a project-owned daily FX rate table `Fx_Daily_Rate`, keyed by
  `(currency_code, rate_date)`, carrying `usd_per_unit`.
- **FR-8**: Convert every transaction amount to USD at the rate for its **business date**
  (`posted_date`) in its `currency_code`. `USD` converts at exactly 1.0.
- **FR-9**: When no rate exists for that currency on that date, use the most recent earlier rate for
  that currency. When no earlier rate exists either, exclude the transaction from every insight and
  count it in `missing_fx_rate_txn_count` (FR-31).

### What counts

- **FR-10**: Include only transactions on a deposit account whose `account_type` is `CHECKING` or
  `SAVINGS`. Exclude `MONEY_MARKET`, `CD` and `IRA`.
- **FR-11**: Count **spending** as a transaction that is `POSTED`, `DEBIT`, on an in-scope account,
  not an internal transfer (FR-14), and not a `REVERSAL` row.
- **FR-12**: Count **income** as a transaction that is `POSTED`, `CREDIT`, on an in-scope account,
  not an internal transfer (FR-14), and not a `REVERSAL` row.
- **FR-13**: Exclude every transaction whose status is `PENDING`, `REVERSED` or `RETURNED` from all
  insight aggregates. A `PENDING` transaction enters the insights on a later run once it posts,
  which the 7-day window guarantees.
- **FR-14**: Treat a transaction as an **internal transfer** when either rule matches, and exclude
  it from spending, income and cash flow:
  - **(a) marked** — its category resolves to the `Transfers` top-level category, or its
    `transaction_type` is one of `TRANSFER_IN`, `TRANSFER_OUT`, `INTERNAL_TRANSFER`.
  - **(b) paired** — a `POSTED` `DEBIT` and a `POSTED` `CREDIT` of the same customer, equal USD
    amount, on two **different** in-scope accounts of that customer, with `posted_date` at most 1
    day apart, where neither row matched rule (a). Each debit pairs with at most one credit; when
    several candidates match, the one with the smallest `transaction_id` wins, so the pairing is
    deterministic.
- **FR-15**: Net **partial refunds and corrections** against the original transaction. For every row
  in `Transaction_Reversal` whose `reversal_type` is `PARTIAL` or `CORRECTION` and whose original
  transaction is still `POSTED`, subtract `reversal_amount_cents` (converted to USD at the
  **original** transaction's business date) from that original transaction's contribution to every
  insight. The netted amount floors at zero. The reversing row itself is excluded by FR-11 and
  FR-12. Apply a reversal only when the reversing transaction's own `posted_date` is on or before
  `run_date`, so a run never sees a refund that had not happened yet and a re-run of an old date
  reproduces what that night knew.
- **FR-16**: Attribute a reversal to the **original** transaction's `posted_date`, month, category,
  merchant and account — never to the reversing row's own date. When that original date falls before
  `window_start`, count the reversal in `late_transaction_count` (FR-31) rather than silently
  dropping it.
- **FR-17**: Resolve each transaction's **category** through `Transaction_Category` to both its
  level-2 category and its level-1 ancestor. A transaction with a null `category_id`, or one that
  does not resolve, is reported under the synthetic category `Uncategorized` at both levels.
- **FR-18**: Resolve each transaction's **merchant** to `merchant_id` and the cleaned merchant name
  from `Merchant_Enrichment`, falling back to the transaction's own `merchant_name`. A transaction
  with no merchant is reported under the synthetic merchant `Unknown merchant`. 45% of debits in the
  test data carry no merchant, so this bucket is normal, not an error.
- **FR-19**: Assign every transaction to the calendar day and calendar month of its `posted_date` in
  UTC.

### Insights

- **FR-20**: For each customer, month and **level-1** category, and for each customer, month and
  **level-2** category, compute spending in USD and a transaction count.
- **FR-21**: For each of those rows, compute **normal spending**: the mean spending of that customer
  in that category over the **3 complete calendar months** before the month, counting a month with
  no spending in that category as zero. Normal spending is null unless the customer's earliest
  in-scope transaction falls on or before the start of that 3-month baseline.
- **FR-22**: Flag **much more than usual** when the month is complete, normal spending is not null,
  the month's spending is at least **50% above** normal spending, **and** the excess is at least
  **$75.00**. Report `excess_usd_cents` and `excess_pct` alongside the flag. The flag is computed
  independently at level 1 and at level 2.
- **FR-23**: For each customer and month, rank merchants by USD spending and keep the **top 5**,
  breaking ties by merchant name ascending then `merchant_id` ascending. Also compute merchant
  spending within each level-2 category, for the category drill-down.
- **FR-24**: For each customer, list their recurring payments from `Recurring_Payment` with a
  **monthly cost** derived from `typical_amount_cents` and `frequency`:
  `WEEKLY x 52/12`, `BIWEEKLY x 26/12`, `MONTHLY x 1`, `QUARTERLY / 3`, `ANNUAL / 12`, rounded
  half-up to whole cents.
- **FR-25**: For each customer, compute the **total monthly recurring cost** as the sum of the
  monthly cost of their `ACTIVE` series only.
- **FR-26**: Flag a recurring payment as **became more expensive** when its latest posted charge is
  at least **5% above** the previous posted charge on the same series **and** at least **$1.00**
  above it. Report `previous_charge_usd_cents`, `latest_charge_usd_cents`, `latest_charge_date`,
  `increase_usd_cents` and `increase_pct` for every series with two or more posted charges, whether
  or not it is flagged. Also surface `typical_amount_usd_cents` and `amount_variance_usd_cents` from
  the catalog as context, without using them for the flag.
- **FR-27**: Flag a spending transaction as an **unusually large purchase** when its USD amount is
  at least **3x** the mean USD amount of that customer's spending transactions in the **90 days
  before** its `posted_date`, **and** at least **$200.00**. A customer with fewer than **5** such
  prior transactions has no baseline and no flag. Report the amount, the baseline mean and the
  ratio.
- **FR-28**: For each customer, account and month, and for each customer and month across all their
  in-scope accounts, compute **cash flow**: income, spending, net (`income - spending`) and savings
  rate (`net / income`). The savings rate is null when income is zero. The customer-level savings
  rate is computed from summed income and summed spending, never as an average of per-account rates.
- **FR-29**: For each customer, account and day, and for each customer and day, compute **daily
  spending** in USD, for the month-overview chart.
- **FR-30**: Mark the month containing the run date as a **partial month** (`is_partial_month`)
  covering days 1 through `run_date`. Suppress the normal-spending comparison for a partial month:
  `normal_spend` and the much-more-than-usual flag are null. Every other month is complete.

### Monitoring

- **FR-31**: Write one `Pipeline_Run_Metric` row per run, keyed by `run_date`, carrying: `run_date`,
  `window_start`, `window_end`, `recomputed_day_count`, `recomputed_months`,
  `transaction_count_processed`, `late_transaction_count`, `missing_fx_rate_txn_count`.
  A transaction is **late** when its enrichment timestamp (`Unified_Transaction.computed_at`) falls
  on the run date but its `posted_date` is before `window_start` — it arrived or changed after the
  window had already moved past it. This number is the evidence for whether 7 days is long enough.
- **FR-32**: Write one `Uncategorized_Spending_Daily` row per day in the window, carrying
  `spend_date`, total spending USD, uncategorized spending USD, the uncategorized **share** of
  spending, total transaction count and uncategorized transaction count. A break in the upstream
  categorization shows up here the next morning.

### API and application

- **FR-33**: Expose one named API operation per screen element (listed under
  [API surface](#api-surface)). Every operation requires a valid JWT. Any signed-in staff user may
  read any customer, so no operation filters by the caller's identity.
- **FR-34**: Serve a staff web application with the five screens below. Every number it displays
  comes from an API operation; the application computes no aggregate of its own.

## Why the window is 7 days

Measured against the catalog's own test data:

| Signal | Observed |
|---|---|
| `posted_date` minus transaction date | 0 days for all 8,608 rows that carry both |
| Reversal lag (`reversed_at` minus original `transaction_at`), n=217 | min 0, median 2, p99 4, **max 5** |
| ACH / wire return lag (`return_effective_date` minus `original_effective_date`), n=39 | min 1, **max 4** |
| Enrichment lag (`computed_at` minus `transaction_at`) | median 0.12 d, p99 0.25 d; 12 rows over 3 d, 2 over 7 d |

7 days covers the observed reversal maximum of 5 days and the return maximum of 4 days with two days
of headroom, which absorbs a weekend or a public holiday in the settlement chain. It keeps the
nightly scan bounded while leaving the enrichment tail (12 rows beyond 3 days) visible through
`late_transaction_count` rather than hidden. If that counter turns out to be consistently non-zero
in production, the window is the single value to raise.

## Sources

All source data comes from the `data-catalog` submodule, included through
`script.include.data_catalog` pointing at `data-catalog/ontology-shared-package.json` with
`config: { "is_batch": true }`. The catalog's `{{environment}}` templating then selects the `-test`
or `-prod` connector set for every table at once, and `is_batch: true` drops the
`source.monitor-interval` that the streaming connectors set.

### `Unified_Transaction` — catalog, silver, `deposits_payments/transactions/enriched_transactions`

The spine of the pipeline: one row per `transaction_id`, already unified across CORE, CARD, ACH and
WIRE rails, already carrying `customer_id`, category, merchant and recurring linkage.

- **Transport**: test — local JSONL via the filesystem connector; prod — Iceberg table
  `deposits_payments.transactions.unified_transaction`, upsert-keyed on `transaction_id`.
- **Format**: JSON in test; Iceberg v2 in prod.
- **Sample payload** (from the catalog's test data, unredacted because it is synthetic):

  ```json
  {
    "transaction_id": "TXN-033", "account_id": "ACCT-577", "customer_id": "CUST-348",
    "transaction_source": "ACH", "source_transaction_id": "ACH-009",
    "transaction_type": "ACH_DEBIT", "debit_credit": "DEBIT",
    "amount_cents": 8033, "currency_code": "USD", "transaction_status": "POSTED",
    "transaction_at": "2023-02-01T06:48:41Z", "posted_date": "2023-02-01",
    "original_description": "SHIELD AUTO INSURANCE COLUMBUS #3028",
    "clean_description": "Shield Auto Insurance Columbus", "channel": "ACH",
    "merchant_id": "MERCH-156", "merchant_name": "Shield Auto Insurance Columbus",
    "mcc_code": null, "category_id": "CAT-023", "category_name": "Insurance",
    "subcategory_name": null, "is_recurring": true, "recurring_payment_id": "REC-095",
    "location": null, "city": null, "state": null, "country": "US",
    "running_balance_cents": 3704033, "is_disputed": false, "is_suspicious": false,
    "fraud_score": 11, "computed_at": "2023-02-01T07:42:31Z"
  }
  ```

  Nullable in practice: `mcc_code`, `category_id`/`category_name` (14.7% null), `merchant_id`/
  `merchant_name` (45% null on debits), `subcategory_name`, `recurring_payment_id`, `location`,
  `city`, `state`. Never null: `transaction_id`, `account_id`, `customer_id`.
- **Volume**: 8,688 rows in test, spanning 2023-02-01 to 2026-09-15 across 492 customers and 1,000
  accounts, 150-400 rows per month. Production volume is unknown — see
  [Open Questions](#open-questions).
- **Delivery**: an upsert snapshot keyed on `transaction_id`, recomputed by the transactions team.
  Replayable.
- **Duplicates and ordering**: one row per `transaction_id`; the catalog's prod connector enforces
  it as the upsert key. No per-key ordering guarantee beyond that.
- **Updates**: mutable. A row is updated as it moves `PENDING` to `POSTED`, `REVERSED` or
  `RETURNED`, and its `category_id` and `merchant_id` can be filled in after it first appears. Status
  distribution in test: `POSTED` 8,481, `REVERSED` 115, `PENDING` 80, `RETURNED` 12.

### `Transaction_Reversal` — catalog, bronze, `deposits_payments/transactions/core_transactions`

One row per `reversal_id`, linking `original_transaction_id` to `reversing_transaction_id`. This is
how a refund reaches this pipeline; there is no separate refund feed.

- 217 rows in test: `FULL` 117, `PARTIAL` 70, `CORRECTION` 30.
- A reversal creates a new `POSTED` transaction with `transaction_type = 'REVERSAL'` (212 such rows
  in `Unified_Transaction`, 193 credits and 19 debits), whose `category_name` is null.
- For a `FULL` reversal the original's status becomes `REVERSED` (115 of the originals). For
  `PARTIAL` and `CORRECTION` the original stays `POSTED` at its full amount (100 of the originals)
  and the refunded part sits in `reversal_amount_cents`. FR-15 is written against exactly this.

### `Account` and `Account_Holder` — catalog, bronze, `deposits_payments/accounts/deposit_accounts`

`Account` gives `account_type` and `account_status`; `Account_Holder` maps accounts to customers.

- 1,000 accounts in test: `CHECKING` 467, `SAVINGS` 315, `CD` 106, `MONEY_MARKET` 80, `IRA` 32. All
  `currency_code` `USD`. Status: `OPEN` 772, `CLOSED` 164, `DORMANT` 44, `FROZEN` 15, `ESCHEAT` 5.
- 1,317 holder rows: `PRIMARY` 1,000, `JOINT` 215, plus beneficiary/custodian/trustee/POA. 336 of
  492 customers hold two or more in-scope accounts, so the account picker on the month overview is
  meaningful.
- A customer's accounts are those where `Account_Holder.is_active` is true. Joint holders each see
  the full account.

### `Transaction_Category`, `Merchant_Enrichment`, `Recurring_Payment` — catalog, silver, `enriched_transactions`

- `Transaction_Category`: 25 rows, a two-level hierarchy through `parent_category_id`. 8 level-1
  categories (Shopping & Dining, Housing & Utilities, Transportation, Entertainment, Financial,
  Income, Health & Insurance, Transfers) over 17 level-2 children, plus the synthetic
  `Uncategorized` this project adds, for 9 rows on the category screen.
- `Merchant_Enrichment`: 214 rows keyed on `merchant_id`, with `clean_merchant_name`.
- `Recurring_Payment`: 181 rows keyed on `recurring_payment_id`, carrying `customer_id`,
  `merchant_name`, `payment_type`, `typical_amount_cents`, `amount_variance_cents`, `frequency`
  (`MONTHLY` 159, `ANNUAL` 9, `QUARTERLY` 6, `BIWEEKLY` 4, `WEEKLY` 3) and `status` (`ACTIVE` 133,
  `ENDED` 26, `UNCERTAIN` 14, `PAUSED` 8).

### `Customer` — catalog, bronze, `customer/customer_data/customer_master`

Used only to resolve a customer id to a display name and status on the search screen. Every other
field in this table is PII or SPII and stays out of this project's outputs.

### `Fx_Daily_Rate` — **owned by this project**

The catalog has no FX rate table, so this project builds one.

- **Transport**: test — a local JSONL file under this project's `testdata/`; prod — an Iceberg
  table in this project's warehouse, upsert-keyed on `(currency_code, rate_date)`, loaded by the
  bank's existing rate feed.
- **Format**: JSON in test, Iceberg v2 in prod.
- **Sample payload**:

  ```json
  {"currency_code": "USD", "rate_date": "2026-09-02", "usd_per_unit": 1.000000, "rate_source": "INTERNAL", "ingested_at": "2026-09-03T01:00:00Z"}
  {"currency_code": "EUR", "rate_date": "2026-09-02", "usd_per_unit": 1.087400, "rate_source": "ECB", "ingested_at": "2026-09-03T01:00:00Z"}
  ```

- **Volume**: one row per currency per calendar day; single digits of currencies, so a few thousand
  rows a year.
- **Duplicates and ordering**: one row per `(currency_code, rate_date)`; last write wins.
- **Test coverage note**: every transaction in the catalog's test data is `USD`, so conversion is an
  identity there. The test data for this table therefore covers `USD` plus `EUR`, `GBP` and `JPY`
  across the test window, including one day deliberately missing a `EUR` rate, so that the join, the
  carry-forward fallback (FR-9) and the missing-rate counter are each exercised directly even though
  no catalog transaction is non-USD.

## Time semantics

- **Business date**: `Unified_Transaction.posted_date`, type `DATE`, UTC. It drives the day, the
  month and the FX rate. In the catalog's test data `posted_date` equals the transaction date for
  every row that carries both.
- **Arrival time**: `Unified_Transaction.computed_at`, `TIMESTAMP_LTZ(3)`, UTC. Used only to
  identify late arrivals (FR-31), never for business grouping.
- **Lateness**: 7 days, as the recomputation window (FR-2). A change to a transaction whose
  `posted_date` is older than `window_start` is counted, not applied.
- **Processing time**: not used anywhere. The job is a batch run parameterized by `run_date`, and
  FR-6 forbids wall-clock values in business logic.
- **Watermarks**: not applicable. This is a batch job over bounded sources; the catalog's silver
  connector tables carry `computed_at` with no watermark in either environment.

## Transformations and aggregations

Every output below is written to Iceberg, keyed as stated, and rewritten only within the scope
stated. `month` is a `DATE` set to the first day of the month, so it sorts and joins cleanly.

| Output table | Key | Grouping / window | Recompute scope | Implements |
|---|---|---|---|---|
| `Customer_Month_Category_L1_Spending` | `(customer_id, month, category_l1_id)` | per customer, month, level-1 category | affected months, in full | FR-20..22, FR-30 |
| `Customer_Month_Category_L2_Spending` | `(customer_id, month, category_l2_id)` | per customer, month, level-2 category, with its level-1 parent | affected months, in full | FR-20..22, FR-30 |
| `Customer_Month_Top_Merchant` | `(customer_id, month, rank)` | top 5 merchants per customer-month | affected months, in full | FR-23 |
| `Customer_Month_Category_Merchant` | `(customer_id, month, category_l2_id, merchant_id)` | merchants within a level-2 category | affected months, in full | FR-23 |
| `Customer_Recurring_Payment` | `(customer_id, recurring_payment_id)` | one row per series, as of run date | full rebuild each run (small) | FR-24, FR-26 |
| `Customer_Recurring_Monthly_Total` | `(customer_id)` | sum over ACTIVE series | full rebuild each run | FR-25 |
| `Customer_Large_Purchase` | `(transaction_id)` | one row per flagged transaction | window days only | FR-27 |
| `Customer_Month_Cash_Flow` | `(customer_id, month)` | per customer-month, all in-scope accounts | affected months, in full | FR-28, FR-30 |
| `Customer_Account_Month_Cash_Flow` | `(customer_id, account_id, month)` | per customer-account-month | affected months, in full | FR-28, FR-30 |
| `Customer_Day_Spending` | `(customer_id, spend_date)` | per customer-day | affected months, in full | FR-29 |
| `Customer_Account_Day_Spending` | `(customer_id, account_id, spend_date)` | per customer-account-day | affected months, in full | FR-29 |
| `Pipeline_Run_Metric` | `(run_date)` | one row per run | append one row | FR-31 |
| `Uncategorized_Spending_Daily` | `(spend_date)` | per day in the window | window days only | FR-32 |

Daily and monthly outputs are rewritten for whole affected months rather than only the window days,
because a reversal landing today can change a day earlier in the same month (FR-16), and a month
total is only correct when every day in it is recomputed together.

**Late-arriving data.** A transaction whose `posted_date` falls inside the window is picked up on the
next run and the affected month is rewritten. A transaction whose `posted_date` falls before
`window_start` is **not** applied — its month has already been frozen — and is counted in
`late_transaction_count` instead. That counter is the agreed signal for revisiting the 7-day choice.

**Ordering and determinism.** Every ranking, every top-N and every pairing in FR-14(b) breaks ties on
an explicit key, so two runs over the same input produce byte-identical output (FR-6).

## API surface

Protocols `GRAPHQL`, `REST` and `MCP`, `endpoints: OPS_ONLY`, so only the named operations below are
reachable. Every operation requires a valid JWT.

### Queries

| Operation | Parameters | Returns | Screen |
|---|---|---|---|
| `CustomerSearch` | `customerId` | customer id, display name, status, count of in-scope accounts | 1 |
| `CustomerAccounts` | `customerId` | the in-scope accounts of that customer only: `accountId`, masked account number, type, status | 2 |
| `MonthOverview` | `customerId`, `month`, `accountId` (optional) | income, spending, net, savings rate, `isPartialMonth` | 2 |
| `DailySpending` | `customerId`, `month`, `accountId` (optional) | one row per day: date, spending USD | 2 |
| `CategorySpending` | `customerId`, `month` | per level-1 category: name, spending, normal spending, `isMuchMoreThanUsual`, excess amount, excess pct, with level-2 children nested | 3 |
| `CategoryMerchants` | `customerId`, `month`, `categoryId` | merchants under that category: name, spending, transaction count | 3 |
| `TopMerchants` | `customerId`, `month` | the top 5 merchants of the month with spending and count | 3 |
| `RecurringPayments` | `customerId` | per series: merchant, type, frequency, monthly cost, latest and previous charge, `becameMoreExpensive`, increase amount and pct, status | 4 |
| `RecurringTotal` | `customerId` | total monthly recurring cost across ACTIVE series | 4 |
| `LargePurchases` | `customerId`, `fromDate` (optional), `toDate` (optional) | date, merchant, category, amount, baseline mean, ratio | 5 |
| `RunMetrics` | `limit` (optional) | the most recent run metric rows | ops |
| `UncategorizedShare` | `fromDate`, `toDate` | per day: total spending, uncategorized spending, share | ops |

`month` is accepted as `YYYY-MM`. Omitting `accountId` means all in-scope accounts of the customer.

### Mutations and subscriptions

None. This pipeline is read-only for its consumers.

### Access

- Vert.x `authKind: ["JWT"]`, HS256, secret from `${SPENDING_INSIGHTS_API_JWT_SECRET}`, issuer
  `spending-insights`, audience `spending-console`.
- Authorization is binary: a valid token grants access to every customer (FR-33). No operation
  filters on a tenant or a caller claim, because any signed-in staff user may open any customer.
- No operation returns SSN, date of birth, address, account number in the clear, or the running
  balance.

### Web application

A single-page application served as static files, five screens, signing in with a staff JWT and
holding the opened customer in shared state so every screen follows it.

1. **Customer search** — enter a customer id, open that customer. Every other screen follows.
2. **Month overview** — month picker and an optional account picker limited to that customer's
   in-scope accounts. Shows money in, money out, what is left, and the share of income left, plus a
   daily spending chart for the chosen month. The current month renders as "month so far" with the
   comparison hidden.
3. **Categories** — level-1 categories for the chosen month with spending, normal spending and the
   much-more-than-usual flag; expanding a row shows its level-2 children, and expanding one of those
   shows the merchants behind it.
4. **Recurring payments** — every series with its monthly cost, the total monthly cost, and a marker
   on the ones that became more expensive.
5. **Large purchases** — date, merchant and amount for each unusually large purchase.

Every figure on every screen maps to one of the operations above. The application performs no
arithmetic across API responses.

  `Fx_Daily_Rate` test file.

  which touches **two** months — August 2026 complete (401 transactions) and September 2026 partial

  month with the comparison suppressed, and the two-month rewrite scope together. `read_from` is

  2026-09-05, which still covers 2026-08-31 while now including the reversal posted on 2026-09-04.

  insight on the next run, which is the whole purpose of the 7-day window.

## Non-functional requirements

- **Freshness**: results for day D are available by 06:00 UTC on day D+1, measured from the source
  tables being complete for day D to the API serving the new rows. The job is scheduled at 02:00 UTC.
- **Run time**: a nightly run completes within 30 minutes at the assumed production volume (see
  [Open Questions](#open-questions)).
- **Read volume**: bounded at roughly 4 months of transactions per run (FR-3), constant as history
  grows. This is the measurable form of "must not read the whole history every night".
- **Throughput**: batch; there is no per-second rate to sustain. Above the assumed volume the run
  takes proportionally longer and the 06:00 UTC target is the first thing to break.
- **Retention**: insight tables keep 36 months of months. `Pipeline_Run_Metric` and
  `Uncategorized_Spending_Daily` keep 400 days. Rows past the boundary are deleted by a separate
  maintenance job, not by this pipeline.
- **PII and sensitive fields**: outputs carry `customer_id`, `account_id`, merchant names, category
  names, dates and USD amounts. No SSN, date of birth, address, contact detail, cleartext account
  number, running balance, or transaction description reaches any output table or any API response.
  Customer display name appears only in `CustomerSearch`. Amounts are GLBA NPI, so every operation
  requires a JWT (FR-33).
- **Compliance**: GLBA, GDPR and CCPA apply through the catalog's Restricted classification. Right
  to erasure is satisfied by deleting a customer's rows from the insight tables; because outputs are
  keyed on `customer_id`, this is a bounded delete and needs no recompute.
- **Availability**: a failed night is recovered by re-running with the same `run_date` (FR-1), which
  is safe because every write is keyed and idempotent (FR-6). The API keeps serving the previous
  night's results while a run is in progress; readers never see a partially written month.

## Open Questions

- **Production transaction volume and customer count.** The test data has 8,688 transactions across
  492 customers; production is unknown, and it decides the parallelism, the run-time target and
  whether 4 months of scan is genuinely cheap. Recommended default: *assume 5 million transactions
  per night across 2 million customers, and size the 30-minute target against that.* Impact if
  wrong: **high** — an order of magnitude more would change the partitioning strategy.
- **Iceberg warehouse location and catalog for this project's outputs.** The catalog uses a Hadoop
  catalog under `${DEPOSITS_PAYMENTS_ICEBERG_WAREHOUSE}`. Recommended default: *a separate
  `spending_insights` warehouse under `${SPENDING_INSIGHTS_ICEBERG_WAREHOUSE}`, Hadoop catalog,
  database `insights`, matching the catalog's conventions.* Impact if wrong: **low** — a config
  change.
- **Who loads `Fx_Daily_Rate` in production.** This project defines and reads the table; the request
  says to build it but does not say which system populates it nightly. Recommended default: *the
  bank's existing treasury rate feed writes the Iceberg table before 01:00 UTC, and this project
  only reads it; a missing day is handled by the carry-forward rule in FR-9.* Impact if wrong:
  **medium** — if nothing populates it, every non-USD transaction falls into the missing-rate
  counter.
- **The paired-transfer rule has no positive test.** FR-14(b) matches zero rows in the catalog's test
  data because every transfer there is already marked, and `counterparty_account_id` is null on all
  8,684 core transactions, so the stronger same-owner check is not available. Recommended default:
  *implement the rule, snapshot its intermediate table as empty, and revisit if production shows
  unmarked transfers.* Impact if wrong: **medium** — unmarked transfers would inflate both spending
  and income.
- **Recurring price increases have no positive test.** Agreed in review: implement the rule, snapshot
  the per-series comparison, accept zero flags in test. Recommended default: *ship as agreed and
  raise the missing test data with the transactions team.* Impact if wrong: **medium** — this is the
  insight the product team wants most and its flagged path will first execute in production.
- **Joint accounts are counted in full for every holder.** A joint account's spending appears in
  full under each active holder, so two joint holders each see the whole amount rather than their
  `ownership_percentage`. Recommended default: *count in full, because a service agent answering a
  call about a shared account wants the account's real total.* Impact if wrong: **medium** — the
  alternative is splitting by ownership percentage, which changes every customer-level number for
  215 joint holdings.
- **Closed, dormant and frozen accounts.** Recommended default: *include transactions from accounts
  in any status, because a closed account's history is still part of how the customer spent; only
  `CustomerAccounts` filters to `OPEN` for the account picker.* Impact if wrong: **low**.
- **Cash withdrawals count as spending.** The 577 `WITHDRAWAL` transactions sit in the
  `Cash Withdrawal` category under `Financial`. Recommended default: *count them as spending, since
  the money did leave the deposit account, and let the category make them identifiable.* Impact if
  wrong: **low** — one predicate.
- **Bank fees and interest.** Recommended default: *count `FEE` and `OVERDRAFT_FEE` (223 rows) as
  spending under `Financial`, and `INTEREST` credits (316 rows) as income, because both change what
  is left at the end of the month.* Impact if wrong: **low**.
- **JWT issuance.** The request specifies JWT but not the issuer. Recommended default: *validate
  HS256 tokens from an existing internal identity provider using a shared secret, and issue no
  tokens from this project.* Impact if wrong: **medium** — a different algorithm or a JWKS endpoint
  changes the Vert.x configuration.
