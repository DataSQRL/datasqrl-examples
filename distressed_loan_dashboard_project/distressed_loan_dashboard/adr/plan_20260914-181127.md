## Requirements Summary

Build a nightly **batch** pipeline that reads loan-payment and delinquency-event sources (auto, personal, mortgage, credit card), reconciles them into exactly-once "payment obligation" records, and computes weekly distress aggregations keyed by **(week, zip code)** and **(week, customer)**. The result is served by a **GraphQL + MCP** API over Postgres for an internal dashboard: a per-zip geographic overview with a two-week trend, a 12-week zip drill-down chart, and a per-zip customer table of distressed customers. Engines: `flink` (batch), `postgres` (serving DB), `vertx` (API). No `kafka` (read-only dashboard, no mutations/subscriptions), no `iceberg`.

A **UI is required** (R7–R14 describe the dashboard's table, search, sort, chart, and drill-down; "visual design details" are deferred, not the dashboard itself). UI steps are included near the end, building a read-only SPA against the GraphQL API.

## Requirements Reference

The requirements document is in-project at `adr/requirements_20260911-205513.md`. The identifiers cited throughout this plan, with their full text:

- **R1** — For each week and each zip code, provide the count and amount of payments due, posted on time, posted late, not posted, and distressed, plus percent distressed and average days late. Each zip code is associated with its state for filtering.
- **R2** — Provide the same measures for each week and each customer.
- **R3** — The aggregations are computed by a nightly batch job.
- **R4** — Each night, the job recomputes all aggregations over the last three months, replacing the previous results. For the buckets, this covers payments due in that period. For average days late, it covers late payments posted in that period, whenever they were due.
- **R5** — Because zip codes are assigned at computation time, a customer who moves is attributed to their new zip code for the entire window on the next nightly run. This is expected behavior.
- **R6** — The split between posted late and not posted for a past week changes on later runs as delinquent payments are paid. The distressed total does not. This is expected behavior.
- **R7** — Display a table with one row per zip code, showing its state and the amounts for payments due, posted late, not posted, and distressed, plus percent distressed and average days late.
- **R8** — The table shows the last two weeks and the trend between them: whether each measure increased or decreased, and by how much. For amounts and average days late, the trend is the percentage change (e.g., $10,000 to $12,000 is +20%). For percent distressed, the trend is the difference between the two percentages (e.g., 5% to 6% is +1%; 9% to 6% is −3%).
- **R9** — Provide a text search field above the table: numeric input shows all zip codes starting with that prefix (e.g., "981"); alphabetic input shows all zip codes in that state (e.g., "PA"); empty input shows all zip codes.
- **R10** — The table shows only zip codes matching the current filter. It can be sorted by any column, ascending or descending, by clicking the column header.
- **R11** — Clicking a zip code in the overview table displays the following below it: a 12-week chart for that zip code (see R12); the zip code's distressed count and distressed amount for the last two weeks, each with its week-over-week percentage change; a customer table limited to customers in that zip code with at least one distressed payment (posted late or not posted).
- **R12** — The chart plots the following for each of the last 12 weeks: amount of payments posted on time; amount of payments distressed; percent distressed; average days late. The first three are by week due. Average days late is by week posted.
- **R13** — The customer table shows, for each customer, the customer ID and enough high-level customer information for the user to look the customer up in other systems, plus all measures from R2.
- **R14** — The customer table can be sorted by any column, ascending or descending, by clicking the column header, so the most distressed customers can be brought to the top.
- **R15** — The dashboard is served by a GraphQL API. All data the dashboard displays comes through this API.
- **R16** — The API supports everything the dashboard does: filtering zip codes by prefix or state, the two-week overview with trends, a zip code's 12-week history, and the customer table with sorting. It also provides all measures from R1 and R2, including those not shown on the dashboard (such as zip-level counts for each bucket).
- **R17** — The same API operations are exposed through MCP, so an AI agent can use them to automate parts of this workflow in the future.

Business definitions (from `adr/requirements_20260911-205513.md` §4) that shape the logic:

- **Buckets (by week due)** — every payment due in a week is exactly one of: **posted on time** (posted by its due date), **posted late** (posted after its due date; includes delinquent payments paid later), **not posted** (not posted, recorded as a delinquency event). No grace periods.
- **Derived** — payments due = on-time + late + not posted; distressed = late + not posted; percent distressed = distressed amount ÷ payments-due amount for the same week, always 0%–100%. Each bucket measured by count and amount; percent distressed uses amounts.
- **Exactly once** — a payment is never counted in both posted late and not posted; a delinquent payment that is eventually paid moves from not posted to posted late; the distressed total for a week is stable.
- **Average days late (by week posted)** — the average days late of all late payments posted during the week, regardless of when due (includes payments due before the reporting window). Only payments eventually posted contribute; unpaid payments (not posted) do not.
- **Geography** — the customer's zip code as it stands when the numbers are computed, applied to all history in the window. A zip's state is used only to filter zips; there are no state-level totals.
- **Customer** — the primary borrower for loans with more than one borrower.
- **Assumption (source)** — a delinquency event is created in the week the missed payment was due.

### Delivery semantics

- **Batch (bounded) read.** `execution.runtime-mode: BATCH`; prod Kafka sources use `scan.bounded.mode = latest-offset`. No at-least-once/streaming dedup concern: each nightly run reads the bounded snapshot and fully recomputes, replacing results.
- **Exactly-once obligation counting** is a data-model reconciliation (below), not a delivery guarantee: a `(account_id, due_date)` that has both a posted payment and a delinquency event is counted once as **posted late**.

## API Contract

`scenario: pipeline`. GraphQL is the authoritative model; MCP tools are auto-generated from it. The API is served from the materialized Postgres tables. `compiler.api.protocols = ["GRAPHQL", "MCP"]` (R15, R17); REST is not required. Endpoints are generated from the tables/functions below (inferred schema; no explicit `.graphqls` file — `/design-api`).

Operations (names are the plan's; the requirements do not fix GraphQL operation names, so these are the chosen names):

1. **`ZipWeeklyAgg`** — query table. Grain `(week_start, zip_code)`. Fields: `week_start`, `zip_code`, `state`, `due_count`, `due_amount_cents`, `on_time_count`, `on_time_amount_cents`, `late_count`, `late_amount_cents`, `not_posted_count`, `not_posted_amount_cents`, `distressed_count`, `distressed_amount_cents`, `percent_distressed`, `avg_days_late`. Optional filter args: `zip_code`, `state`, `week_start`. Satisfies R1 + R16 ("all measures from R1, including zip-level counts for each bucket").
2. **`CustomerWeeklyAgg`** — query table. Grain `(week_start, customer_id)`. Fields: `week_start`, `customer_id`, `full_name`, `zip_code`, `state`, plus the same measures as `ZipWeeklyAgg`. Optional filter args: `customer_id`, `zip_code`, `week_start`. Satisfies R2.
3. **`ZipOverview`** — query table. One row per zip over the last two complete weeks. Fields: `zip_code`, `state`, and for each of the current and prior week — `cur_week_start`, `prev_week_start`, `cur_due_amount_cents`, `prev_due_amount_cents`, `due_amount_trend_pct`, `cur_late_amount_cents`, `prev_late_amount_cents`, `late_amount_trend_pct`, `cur_not_posted_amount_cents`, `prev_not_posted_amount_cents`, `not_posted_amount_trend_pct`, `cur_distressed_amount_cents`, `prev_distressed_amount_cents`, `distressed_amount_trend_pct`, `cur_distressed_count`, `prev_distressed_count`, `distressed_count_trend_pct`, `cur_percent_distressed`, `prev_percent_distressed`, `percent_distressed_trend_pp`, `cur_avg_days_late`, `prev_avg_days_late`, `avg_days_late_trend_pct`. Optional filter args: `zip_code` (prefix), `state`. Satisfies R7, R8, R9, R10, R16.
4. **`ZipHistory(zip_code: String!)`** — table function returning the 12 most recent complete weeks for a zip, ordered by `week_start` ascending. Fields per row: `week_start`, `on_time_amount_cents`, `distressed_amount_cents`, `percent_distressed`, `avg_days_late`. Satisfies R11 chart, R12.
5. **`ZipDistressSummary(zip_code: String!)`** — table function returning the zip's distressed count and amount for the last two weeks with week-over-week percentage change: `zip_code`, `cur_distressed_count`, `prev_distressed_count`, `distressed_count_trend_pct`, `cur_distressed_amount_cents`, `prev_distressed_amount_cents`, `distressed_amount_trend_pct`. Satisfies R11 header.
6. **`DistressedCustomers(zip_code: String!)`** — table function returning customers in the zip with ≥1 distressed payment in the last two weeks, with `customer_id`, `full_name`, and the R2 measures (last-two-weeks values + trend). Satisfies R11 customer table, R13, R14.

**Trend semantics** (R8, R11): amounts and average days late use percentage change `(cur − prev) / prev × 100`; percent distressed uses percentage-point difference `cur − prev`. Both are `NULL` when the prior value is `NULL` or zero (see `## Assumptions`).

## Acceptance Criteria

- *(R1/R4)* A payment posted on or before its due date counts only in posted on time. A payment posted one day after its due date counts as posted late.
- *(R4)* A payment due in week 1 that is not made appears in week 1's not posted bucket. If that payment is paid in week 4, it moves to week 1's posted late bucket, is removed from not posted, and week 1's distressed count and amount do not change.
- *(R4)* That payment's days late count toward week 4's average days late (posted in week 4). A payment due five months ago and paid this week, 150 days late, counts toward this week's average days late and does not appear in any bucket.
- *(R1)* If a zip code has $100,000 in payments due for a week, of which $3,000 were posted late and $2,000 were not posted, percent distressed shows 5%. Percent distressed is always between 0% and 100%.
- *(R1)* For each week, posted on time plus distressed equals payments due, by both count and amount.
- *(R1/R2)* For a given week, a zip code's bucket counts and amounts equal the sum of the figures of all its customers (R2), including customers not shown in the drill-down. A loan with two borrowers is counted once, under the primary borrower and the primary borrower's zip code.
- *(R3/R4/R5)* A payment posted since the previous nightly run is reflected after the next run. After a customer's zip code changes, the next nightly run attributes all of that customer's payments in the window to the new zip code.
- *(R8)* If a zip code's distressed amount went from $10,000 to $12,000 between the last two weeks, the overview shows +20%. If its percent distressed went from 5% to 6%, the overview shows +1%; from 9% to 6%, −3%.
- *(R9/R10)* Entering "981" shows only zip codes beginning with 981. Entering "PA" shows all zip codes in Pennsylvania and no state total row. Clicking any column header in the overview table sorts by that column; clicking again reverses.
- *(R11/R12/R13/R14)* Clicking a zip code shows a 12-week chart, the zip code's distressed count and amount with week-over-week change, and a table of that zip code's customers with at least one distressed payment, each with a customer ID and all measures. A customer with no distressed payments does not appear. Clicking any column header in the customer table sorts; clicking again reverses.
- *(R15/R16/R17)* Every figure shown on the dashboard is retrievable through the GraphQL API. Zip-level counts for every bucket are available through the API. The same queries made through MCP return the same results as through GraphQL.

## Data Quality & Observability

**Build**

- **`DQ_UnresolvedObligation`** (DQ) — reads the normalized payment/delinquency obligation rows before aggregation. A row here is an obligation whose `account_id` or `customer_id` fails to resolve to an account/loan or a customer (e.g. a payment whose `loan_id` has no matching loan row, or a delinquency `customer_id` with no `Customer`), which the pipeline would otherwise drop or mis-bucket to a null zip. Each row names the obligation key and the missing reference so it can be investigated. Supports R1/R2 correctness and R16 visibility. Built from a LEFT JOIN to the account/customer tables, keeping the unmatched side.
- **`DQ_NegativeAmount`** (DQ) — reads the payment and delinquency sources. A row is a payment or delinquency amount `<= 0` (numeric sanity). Supports the "percent distressed always 0–100%" and "amounts taken as provided" invariants. Flink does not flag this on its own.
- **`OB_SourceIngestionStats`** (OB) — counts records per source per nightly run (a `UNION ALL` of the six source tables tagged with `source_name`, grouped by `source_name` and ingestion date). A missing row or a dropped count for one source makes an input problem visible. Because this is a nightly batch (not streaming), counts are per-run/day rather than per-hour; this deviation from the hourly pattern is deliberate.

**Skip**

- **Hourly ingestion stats (per-source per-hour)** — not applicable to a nightly batch recompute; replaced by the per-run `OB_SourceIngestionStats`.
- **Enum-validity / referential-integrity runtime tables over the catalog's own tables** (valid `loan_type`, `event_type`, `payment_status`, customer/address referential integrity) — already covered by the catalog's build-time `/*+test(no_rows) */` assertions (e.g. `customer/customer_ontology.sqrl` lines 63–92); they validate test data at build time, and re-implementing them as runtime tables would duplicate the catalog without new signal. The two DQ tables above cover the reconciliation/amount rules the catalog does not.
- **A "customer without current address" DQ table** — the normalization join uses the customer's current zip; a customer missing a current address would surface in `DQ_UnresolvedObligation` (unresolved geography), so a separate table is redundant.

**Reuse**

- Catalog source schemas and reference tables (customer, address, loans, accounts, borrowers) — reused via `script.include`, not rebuilt.
- Catalog build-time `/*+test(no_rows) */` assertions — reused as-is; not duplicated in this project.

## Technical Decisions

- **Nightly full recompute over batch mode.** Chosen over an incremental streaming pipeline because R3/R4 mandate a nightly job that recomputes the last three months and replaces prior results, and R5/R6 require "recompute attributes everything to the current zip" and "distressed total stays stable while late/not-posted split changes" — both are trivially satisfied by a full batch recompute over a bounded read, and hard to guarantee incrementally. `execution.runtime-mode = BATCH`.
- **Engines `flink` + `postgres` + `vertx`, omitting `kafka`/`iceberg`.** The dashboard is read-only (queries only), so there is no `SUBSCRIBE` or `/*+engine(kafka)*/` mutation to require `kafka`, and no data-lake sink to require `iceberg`. `postgres` serves the API from materialized aggregate tables; `vertx` exposes GraphQL/MCP.
- **Reuse the catalog's `_schema` tables via namespaced import + `LIKE`, with this project's own connectors.** Chosen because the catalog is the authoritative source for these tables (reusing column definitions avoids drift), but the acceptance criteria need controlled test data the catalog's test files do not provide. Namespaced (non-wildcard) import keeps the imported `_schema` tables private to the connector scripts so they never appear in this project's API.
- **Unified obligation grain `(account_id, loan_vehicle, customer_id, due_date, amount_cents, posted_date, days_late)`** with exactly-once dedup on `(account_id, due_date)`. Chosen because the two sources (posted payments and missed-payment delinquency events) both describe the same underlying "scheduled payment" identified by account + due date, and the requirements demand each distressed payment be counted exactly once. A posted payment takes precedence over a matching delinquency event (→ posted late).
- **Payment-status filter: `APPLIED` (loans/mortgage) and `POSTED` (cards), excluding `PENDING`/`RETURNED`/`REVERSED`; delinquency filter to `event_type = 'MISSED_PAYMENT'`.** Chosen so only payments actually made and payments actually missed enter the buckets; lifecycle events (`DELINQUENCY_START`/`CURED`/`CHARGE_OFF`) are not per-payment obligations.
- **Two groupings joined on `(week_start, …)`.** Buckets (and `percent_distressed`) group by `week_due`; `avg_days_late` groups by `week_posted`. A single `ZipWeeklyAgg`/`CustomerWeeklyAgg` row carries both (bucket columns are by due-week, `avg_days_late` is by posted-week), joined by full outer join so a week with due payments but no late postings has `avg_days_late = NULL`. This is mandated by R4/R12, which assign the two metrics different week semantics.
- **Monday-start ISO week via `DATE_TRUNC('week', …)`; window `[as_of_date − 13 weeks, as_of_date)`.** `as_of_date` is a `script.config` value (fixed `2026-09-14` in test, run date in prod) so the window and "last two complete weeks" are deterministic and testable.
- **Geography = customer's current zip** from `Customer_Address` (`is_current`, prefer `address_type = 'PRIMARY'`), applied to the whole window. Chosen to satisfy R5 (zip assigned at computation time) without per-period address history.
- **Amounts in cents (BIGINT), `percent_distressed` as `DECIMAL(5,2)` = distressed ÷ due × 100, `NULL` when due = 0.** Chosen to match the catalog's cent-denominated amounts and avoid float drift; the dashboard formats currency.
- **Trend semantics**: percentage change for amounts and avg days late, percentage-point difference for percent distressed, both `NULL` when the prior value is `NULL` or zero. Chosen to match R8's two trend definitions and avoid divide-by-zero.
- **Inferred GraphQL schema (no explicit `.graphqls`), `compiler.api.protocols = ["GRAPHQL", "MCP"]`.** Chosen because the requirements fix API capabilities but not a static schema; MCP tools auto-generate from the same GraphQL model (R17). REST is omitted (not requested).

## Assumptions

- **Reconciliation key and delinquency due-date**: A `MISSED_PAYMENT` delinquency event's implied due date is `event_date`, and the obligation match key is `(account_id, due_date)`. Rationale: the requirements state a delinquency event is created in the week the missed payment was due, and the payment tables preserve the scheduled `due_date` even for late payments. [impact: high]
- **Primary borrower mapping**: loans → `primary_borrower_customer_id`, mortgage → `Mortgage_Borrower` with `borrower_type = 'PRIMARY'`, cards → `Credit_Card_Account.primary_customer_id`. Rationale: the requirements say "primary borrower", and these are the catalog's primary-borrower fields. [impact: high]
- **Payment/delinquency status filters**: only `APPLIED`/`POSTED` payments and `MISSED_PAYMENT` delinquency events count. Rationale: prevents returned/reversed payments and lifecycle events from distorting buckets; if the real source uses different status codes, the filter values are localized. [impact: high]
- **Week definition**: Monday-start ISO weeks in UTC; "last two weeks" = the two most recent complete weeks; the window always covers ≥12 complete weeks. Rationale: Monday/UTC is the conventional default; the 13-week window guarantees 12 complete weeks for the chart. [impact: medium]
- **Customer table time window**: last two weeks with trend (like the overview); a customer appears if they have ≥1 distressed payment in that window. Rationale: open question #1; this is the only choice consistent with "limited to customers with at least one distressed payment" plus R2's per-week measures and the overview's trend style. [impact: medium]
- **Loan-vehicle breakout/filter is out of scope** for the dashboard (open question #2); `loan_vehicle` is used internally to normalize sources but not exposed as a filter. [impact: medium]
- **Customer information fields**: `customer_id` + `full_name` (+ `primary_state`, `primary_postal_code`). Rationale: enough to look the customer up in other systems (R13). [impact: low]
- **State input format**: two-letter uppercase abbreviation; the search field treats all-numeric input as a zip prefix and alphabetic input as a state code (case-insensitive). Rationale: open question #10; two-letter codes match the catalog's `state_province`. [impact: low]
- **Empty/zero trend and empty averages**: trend is `NULL` when the prior value is `NULL`/zero; `avg_days_late` is `NULL` when no late payments posted; `percent_distressed` is `NULL` when nothing was due. Rationale: open question #6; `NULL` is the safest "no data" signal for the UI to render. [impact: low]
- **Access/authentication and masking (open question #3) are out of scope** for this iteration: the API is served without JWT enforcement, and no masking/audit logging is added. Rationale: the requirements defer access/privacy to the design teams; the customer-level tables remain exposed as specified by R13/R16. [impact: medium]
